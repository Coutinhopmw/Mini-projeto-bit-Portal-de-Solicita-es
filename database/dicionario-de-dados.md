# Dicionário de dados

Portal de Solicitações Internas. Descreve cada tabela e cada coluna do banco PostgreSQL, conforme criado por `database/schema.sql` (ou por `python manage.py migrate`). O modelo e as decisões estão em [docs/modelo-de-dados.md](../docs/modelo-de-dados.md), e o diagrama em [docs/diagrama-er.png](../docs/diagrama-er.png).

Convenções das tabelas:

- **Nulo:** `Não` é NOT NULL; `Sim` aceita NULL.
- **Padrão:** valor aplicado pelo banco quando a coluna não é informada. `agora` é `STATEMENT_TIMESTAMP()`, a data e a hora do servidor. A coluna `id` de todas as tabelas é `GENERATED BY DEFAULT AS IDENTITY`.
- **PK, FK, UQ, CK:** chave primária, chave estrangeira, único e CHECK.
- Os identificadores citados entre colchetes (RN, D) são as regras de negócio e as decisões do projeto.

## Visão geral

| Tabela | Finalidade | Registros no seed |
| :-- | :-- | :-- |
| usuarios | Pessoas que acessam o portal e o papel de cada uma | 4 |
| categorias | Tipos de solicitação (TI, RH, Compras, Financeiro, Infraestrutura) | 5 |
| solicitacoes | Demandas registradas pelos colaboradores | 12 |
| historico_status | Cada mudança de status de uma solicitação, inclusive a criação | 24 |

Relacionamentos: `solicitacoes` pertence a uma `categorias` e a um `usuarios` (o solicitante); `historico_status` pertence a uma `solicitacoes` e a um `usuarios` (quem alterou).

## Tabela: usuarios

Pessoas que acessam o portal. Não há autocadastro: os usuários são criados pelo seed ou pelo Django Admin (D08).

| Coluna | Tipo | Nulo | Padrão | Restrições | Descrição |
| :-- | :-- | :-- | :-- | :-- | :-- |
| id | bigint | Não | identidade | PK | Identificador do usuário. |
| nome | varchar(150) | Não | | | Nome completo, exibido nas telas. |
| login | varchar(50) | Não | | UQ | Nome de acesso. É único e não diferencia o usuário na mensagem de erro do login (RN19). |
| senha_hash | varchar(128) | Não | | | Hash da senha no formato PBKDF2-SHA256 do Django. A senha em texto nunca é gravada. |
| papel | varchar(20) | Não | `SOLICITANTE` | CK `usuarios_papel_valido`: `SOLICITANTE` ou `ATENDENTE` | Perfil de uso (D01). O Solicitante vê as próprias solicitações; o Atendente vê todas e altera o status. |
| ativo | boolean | Não | `true` | | Indica se o usuário pode entrar. Usuário inativo não faz login. |
| administrador | boolean | Não | `false` | | Libera o acesso ao Django Admin, onde se gerenciam usuários e categorias (D01). |
| criado_em | timestamptz | Não | agora | | Data e hora do cadastro. |
| ultimo_acesso | timestamptz | Sim | | | Data e hora do último login. Nulo até o primeiro acesso. |

## Tabela: categorias

Tipos de solicitação. Ficam em tabela própria para que o administrador inclua ou inative categorias sem alterar o código (D07).

| Coluna | Tipo | Nulo | Padrão | Restrições | Descrição |
| :-- | :-- | :-- | :-- | :-- | :-- |
| id | bigint | Não | identidade | PK | Identificador da categoria. |
| nome | varchar(60) | Não | | UQ | Nome exibido no formulário e nos filtros. Não se repete. |
| ativa | boolean | Não | `true` | | Só categorias ativas aparecem no formulário de cadastro (RN16). Uma categoria em uso não é excluída, apenas inativada. |

## Tabela: solicitacoes

Demandas registradas pelos colaboradores. O código legível (`SOL-00042`) não é coluna: é montado pela aplicação como `SOL-` mais o `id` com cinco dígitos (D06).

| Coluna | Tipo | Nulo | Padrão | Restrições | Descrição |
| :-- | :-- | :-- | :-- | :-- | :-- |
| id | bigint | Não | identidade | PK | Identificador da solicitação e base do código exibido. |
| titulo | varchar(150) | Não | | CK `solicitacoes_titulo_minimo`: no mínimo 3 caracteres sem contar os espaços das pontas | Título resumido da demanda. Aceita buscas parciais (RN13). |
| descricao | varchar(2000) | Não | | CK `solicitacoes_descricao_minima`: no mínimo 10 caracteres sem contar os espaços das pontas | Descrição detalhada da demanda. |
| status | varchar(20) | Não | `ABERTO` | CK `solicitacoes_status_valido`: `ABERTO`, `EM_ATENDIMENTO` ou `CONCLUIDO` | Situação atual (RN08). A sequência é Aberto, Em Atendimento e Concluído, sem retorno nem salto (RN09), validada nos services. |
| criado_em | timestamptz | Não | agora | | Data e hora de abertura, definida pelo servidor (RN03). Base do filtro por período. |
| atualizado_em | timestamptz | Não | agora | | Data e hora da última alteração. A aplicação o atualiza a cada gravação. |
| categoria_id | bigint | Não | | FK → categorias(id) | Categoria da solicitação. Uma categoria em uso não pode ser excluída. |
| solicitante_id | bigint | Não | | FK → usuarios(id) | Usuário que abriu a solicitação, definido pelo servidor a partir da sessão (RN03). Só ele edita e exclui, e só com status `ABERTO` (RN05, RN06). |

## Tabela: historico_status

Um registro para a criação e um para cada mudança de status, gravados na mesma transação da alteração (D11). A exclusão de uma solicitação remove o histórico dela (D05).

| Coluna | Tipo | Nulo | Padrão | Restrições | Descrição |
| :-- | :-- | :-- | :-- | :-- | :-- |
| id | bigint | Não | identidade | PK | Identificador do registro de histórico. |
| status_anterior | varchar(20) | Sim | | CK `historico_status_anterior_valido`: nulo ou um dos três status; CK `historico_status_muda`: diferente de `status_novo` | Status antes da mudança. Nulo no registro da criação, que não tem status anterior. |
| status_novo | varchar(20) | Não | | CK `historico_status_novo_valido`: `ABERTO`, `EM_ATENDIMENTO` ou `CONCLUIDO` | Status depois da mudança. Na criação, é sempre `ABERTO`. |
| alterado_em | timestamptz | Não | agora | | Data e hora da mudança. |
| alterado_por_id | bigint | Não | | FK → usuarios(id) | Quem fez a mudança: o solicitante na criação e o atendente nas transições (RN10). |
| solicitacao_id | bigint | Não | | FK → solicitacoes(id) | Solicitação a que o registro pertence. |

## Índices

| Tabela | Índice | Colunas | Uso |
| :-- | :-- | :-- | :-- |
| solicitacoes | solicitacoes_status_idx | status | Filtro por status e contagens do dashboard. |
| solicitacoes | solicitacoes_criado_em_idx | criado_em | Filtro por período e ordenação da mais recente para a mais antiga (RN15). |
| solicitacoes | solicitacoes_categoria_id_… | categoria_id | Filtro por categoria. Criado pelo Django na chave estrangeira. |
| solicitacoes | solicitacoes_solicitante_id_… | solicitante_id | Visibilidade do Solicitante, aplicada em toda consulta (D04). Criado pelo Django na chave estrangeira. |
| historico_status | historico_solicitacao_idx | solicitacao_id, alterado_em | Histórico de uma solicitação em ordem cronológica. |
| historico_status | historico_status_alterado_por_id_… | alterado_por_id | Criado pelo Django na chave estrangeira. |

Além desses, o banco tem os índices das chaves primárias e das restrições UNIQUE (`login` e `nome`), e o Django acrescenta um índice `_like` em cada uma dessas duas colunas para buscas por prefixo.

## Integridade na exclusão

As chaves estrangeiras são `DEFERRABLE INITIALLY DEFERRED` e não têm cascata no banco. O `CASCADE` do histórico (D05) e o `PROTECT` de categorias e usuários são aplicados pelo ORM do Django. Por isso, um `DELETE` direto em SQL numa solicitação que tenha histórico, ou numa categoria ou usuário referenciado, é bloqueado pelo banco. A exclusão deve passar pelo service da aplicação.

## Tabelas internas do Django

O `python manage.py migrate` também cria tabelas do próprio framework, que não fazem parte do domínio e não são descritas aqui: `django_migrations`, `django_content_type`, `django_admin_log`, `django_session`, `auth_permission` e `auth_group` com suas relações. O `database/schema.sql` contém apenas as quatro tabelas do portal.

## Conferência com os scripts

Este dicionário foi conferido contra o banco criado a partir dos scripts: nomes, tipos, tamanhos, nulidade, padrões, chaves e CHECKs coincidem. Repetir a conferência após qualquer mudança de migration, e de novo no fechamento do projeto.
